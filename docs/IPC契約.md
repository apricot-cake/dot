# IPC のデータ契約

IPC は、アプリの画面とメインプロセスの間でデータをやり取りする仕組みです。この文書では、そのデータ形式と検証方法を説明します。スキーマは、各項目の型や必須条件を定義したものです。

保存済みバッジの投稿リンクは `app/src/shared/post-link.ts` のスキーマで検証します。`dot://post` は保存済み投稿の表示だけを行い、保存や削除は行いません。個別保存は保存時のメディア URL も照合します。起動前に届いたリンクは、レンダラーの初回読み込み後に `take-post-link` で受け取ります。

入力は `app/src/shared/ipc-inputs.ts`、保存データの構造と既定値は `data-schemas.ts` に定義します。型は Zod の `input` / `output` から導きます。チャネルの戻り値は `ipc-results.ts` を main と preload の両端で使います。

`activity-ipc.ts` は全チャネルの送信元と引数を検証します。配備済みのアプリ入口、または明示した開発サーバーの最上位フレームだけを受け付けます。入力が不正な場合はハンドラを実行しません。ログにはチャネルと問題の位置・種類だけを記録し、ペイロード全体は記録しません。

DB の置換処理も共通スキーマを使います。IPC 以外に ZIP 取り込みからも呼ばれるため、検証に成功してから既存行を置き換えます。省略可能な値の既定値と、不正値の読み替えは区別します。不正値を空配列へ変えて保存しません。

## 契約の変更

IPC、設定、フォルダ、タグ、プロフィール、タブ、アーカイブの保存形式を変更するときは、共通スキーマ、メインプロセス、プリロードスクリプト、レンダラーを同じ変更で更新します。不正な値を既定値や空配列に読み替えて保存しません。ZIP の整理情報は統合前に検証し、不正な値があればデータベースのトランザクションを取り消します。

## 投稿の取り込み・復旧

投稿の保存形式・既定値と型は `native-host/post-schemas.mts` で共有します。`post-record.mts` は検証後に取得時刻を付け、画像と動画の保存先を整理します。タグ名の NFKC 正規化と重複除去は、文字列配列の検証後に行います。

一覧表示の投稿・プロフィールは `app/src/shared/post-view-schemas.ts` で保存スキーマから導きます。DB の読み出し、IPC、レンダラーで同じ型を使います。ゴミ箱やタグの再計算中には存在しない集計値を、表示用の型で区別します。切り抜き範囲とメディアの型も保存スキーマを共有します。

ネイティブ メッセージングの要求・応答と取得前のメタデータは `native-host/protocol.mts` に定義します。要求が不正ならダウンロードや保存を始めず、既存の失敗応答に項目の位置とエラーの種類を載せます。ペイロードの値は載せません。拡張機能の投稿型と初期値も、この共有定義から導きます。

取込キューは `InboxEnvelopeSchema` で投稿と、それを包む管理情報（エンベロープ）を検証します。ハッシュは、既定値を補う前のレコードで照合します。ZIP の投稿と復元フラグは保存前に検証します。不正な投稿を含む ZIP ではデータベースのトランザクションを取り消します。既にコピーした媒体ファイルは残るため、DB とファイルの操作全体を一度に確定・取り消しできるわけではありません。

`restorePostFlags` は `PostFlagsSchema` を使います。ゴミ箱からの復元はファイルを移す前に投稿・フラグ・所属を検証します。投稿とフラグは同じ DB トランザクションで戻します。復元先のフォルダが既に削除されていた場合の所属判定は、構造検証とは別の処理として残ります。

DB の JSON 列は保存時と同じスキーマで読みます。破損した列やゴミ箱のレコードは警告を記録し、表示できるデータだけを返します。この読み取りで保存内容を書き換えません。新規の取り込みで不正値を欠損へ読み替えることとは区別します。

## 取得元の必須値と欠損

取得元の応答は項目ごとに検証し、利用できる値を共通の保存形式へ取り込みます。型の不一致、必須項目の欠落、JSON の解析失敗、通信失敗では保存を拒否しません。解釈できない項目は反映せず、取得不足と診断を残します。値を推測で補完したり、取得不足を正常な空値として扱ったりしません。

取得元の契約は `extension/utils/extractor/api-schemas.ts` と `bluesky-api-schemas.ts` に定義します。Bluesky の投稿件数は公式 Lexicon で省略できますが、本文・作成日時や投稿の識別情報は必須です。X の埋め込み用 API と pixiv AJAX は公開された開発者 API ではないため、実応答にないフィールドを必須値として扱いません。X の `possibly_sensitive` は省略可能とします。X API v2 の契約を埋め込み用 API の根拠には使いません。

本文、識別情報、日付、プロフィール、件数、メディア、引用、リンクカードは、利用できる項目を独立して反映します。一つの項目の不一致で他の有効な情報を失わないようにします。本文や画像を何も取得できなくても、利用者が指定した URL と保存時刻を不完全な投稿として残します。一覧には URL を表示し、再取得は同じ保存 ID の投稿へ統合します。

工程の失敗は `acquisitionIssues` の `post`・`profile`・`media` と、`invalidResponse`・`fetchFailed`・`unavailable` で区別します。検証済みの情報を返す場合も、取得できなかった範囲を残します。メディアの一部を取得できない場合や未知の形式を受け取った場合は、正常な「メディアなし」や完全取得として扱いません。

`acquisitionComplete` は取得不足が残るレコードを不完全と判定します。再取得が不完全な場合は、保存済みの本文、プロフィール、メディアを空の値で置き換えません。完全取得と不完全取得の統合方針は、共通の保存処理で扱います。

保存成功と取得完了は区別します。URL だけの保存も成功応答を返し、取得不足の通知に再取得操作を付けます。送信元、URL、ダウンロード先、ファイルの安全性、処理量の上限は引き続き検査します。内部の保存形式と IPC のスキーマは維持します。

取得の診断には固定の工程名、HTTP 状態、失敗分類、検証項目の位置を記録します。応答の値、URL、認証情報、動的なキー、例外のメッセージは転送しません。診断用のコールバックの失敗で取得処理を止めません。

フォルダの親子関係、参照先の存在、タグの正規化・衝突、トランザクション、URL と投稿 ID の対応付けは構造検証とは別の処理として残ります。

## 検証

変更に近いテストから実行します。通常は `pnpm run check`、拡張機能を変更した場合は `pnpm run check:ext`、保存経路や起動処理を変更した場合は `pnpm run test:integration` も実行します。配備済みのアプリまたは開発用 Chrome で確認する手順は [CONTRIBUTING.md](CONTRIBUTING.md) を参照してください。

## 根拠

入力検証と型導出は [Zod](https://zod.dev/basics)、送信元検証は [Electron のセキュリティガイド](https://www.electronjs.org/docs/latest/tutorial/security#17-validate-the-sender-of-all-ipc-messages)に基づきます。Zod の採用は Electron の必須仕様ではなく、このプロジェクトで選んだ実装方式です。

Bluesky の [postView](https://github.com/bluesky-social/atproto/blob/main/lexicons/app/bsky/feed/defs.json) と [post](https://github.com/bluesky-social/atproto/blob/main/lexicons/app/bsky/feed/post.json) の必須項目・省略可能項目を参照してください。
