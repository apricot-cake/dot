# 配布とストア提出

dot は、Windows デスクトップアプリと Chrome 拡張機能を組み合わせて使うメディアライブラリです。デスクトップアプリは Microsoft Store、拡張機能は Chrome ウェブストアで配布する方針です。

この文書は、配布に関する決定事項と提出フローの設計案をまとめます。2026年10月11日時点では、MSIX 化とストア提出の自動化は未実装です。現在の開発・配布コマンドは [CONTRIBUTING.md](CONTRIBUTING.md) を参照してください。

## 決定した配布方式

| 対象 | 配布先 | パッケージ形式 | 作成ツール |
| --- | --- | --- | --- |
| Windows デスクトップアプリ | Microsoft Store | MSIX | Electron Forge の公式 MSIX Maker |
| Chrome 拡張機能 | Chrome ウェブストア | Manifest V3 の拡張機能をまとめた ZIP | 既存の拡張機能ビルド・パッケージ処理 |

MSIX は、Windows がインストール、更新、アンインストールを管理するパッケージ形式です。アプリの更新は Microsoft Store に任せる方針です。

初回公開の対応環境は Windows 11、CPU アーキテクチャは x64 とします。最低ビルドは `10.0.22000.0` を候補とし、依存ツールに追加要件があれば引き上げます。インストール可能な最低ビルドと、動作確認するサポート中の Windows リリースは分けて管理します。同梱ツールとネイティブモジュールを含めた製品全体の動作検証は未完了です。

アプリと拡張機能のバージョン番号は独立して管理します。対応する組み合わせと更新時の互換性は、番号の一致とは別に確認します。

Electron Forge を継続して使い、MSIX の生成には `@electron-forge/maker-msix` を採用します。この Maker は公式ドキュメントで experimental とされています。依存バージョンを固定し、更新時にはパッケージ生成とインストール後の動作を再検証します。[Forge の MSIX 対応](https://www.electronforge.io/config/makers/msix)

Windows アプリの一般配布は Microsoft Store に一本化します。GitHub Releases での一般配布は行わず、GitHub Actions の成果物は検証用に使います。

## インストール先と保存先

### MSIX 版

MSIX 版では、アプリ本体、アプリの内部データ、利用者のライブラリを分けます。次の配置を実装方針とします。

| 対象 | 配置 | 扱い |
| --- | --- | --- |
| アプリ本体・同梱ツール | Windows が管理するパッケージフォルダ | 読み取り専用。インストール先を固定パスで参照しない |
| 永続的な設定 | パッケージ専用の `LocalState` | アプリの設定を保存する |
| キャッシュ | パッケージ専用の `LocalCache` | 再作成できるデータを保存する |
| 一時ファイル | パッケージ専用の `TempState` | 永続保存を必要としない作業用データを保存する |
| ライブラリ | 利用者が選んだ、パッケージ外のフォルダ | メディアとライブラリのデータベースを保存する |

本体のインストール先は通常 `C:\Program Files\WindowsApps\…` です。内部データは通常 `%LOCALAPPDATA%\Packages\<PFN>\…` に配置されます。PFN は Windows がアプリを識別するパッケージファミリ名です。実装では Windows が提供する場所を解決し、これらのパスを組み立てて固定しません。[MSIX の配置と仮想化](https://learn.microsoft.com/en-us/windows/msix/msix-containerization-overview)

ライブラリの既定は `%USERPROFILE%\dot\Library` とし、利用者が保存先を変更できる既存の方針を維持します。ライブラリはアプリのアンインストール時に削除する対象に含めません。

この配置は Windows のパッケージアプリ向けの構成です。Electron の既定の保存先とは異なるため、`userData` とキャッシュの保存先を明示的に設定する必要があります。

### 主作業ツリーからの直接起動

主作業ツリーから直接起動するアプリには、MSIX のパッケージ ID がありません。設定と実行時データは、MSIX 版のパッケージ専用領域とは別に保存します。

| 対象 | 保存先 |
| --- | --- |
| 設定（`userData`） | `%APPDATA%\dot-Workspace` |
| Chromium のセッションデータ（`sessionData`） | `%LOCALAPPDATA%\dot-Workspace\Session` |
| ログ | `%LOCALAPPDATA%\dot-Workspace\Logs` |
| 一時ファイル | OS の一時フォルダ内に実行ごとに専用ディレクトリを作成 |
| ライブラリ | 利用者が選んだ場所。設定・キャッシュ領域とは分ける |

Electron の設定保存先は、Windows では `%APPDATA%` 配下が既定です。セッションデータにはキャッシュだけでなく、Cookie や `localStorage` なども含まれます。設定とは分けて保存しますが、セッションデータ全体を削除可能なキャッシュとして扱いません。保存先は Electron の初期化前に設定します。[Electron の保存先 API](https://www.electronjs.org/docs/latest/api/app#appgetpathname)

`dot-Workspace` は主作業ツリーからの起動を区別する、このプロジェクト内の名称です。日常利用でも同じ場所を使います。隔離検証の設定とライブラリは、既存のサンドボックス内へ分離します。これらの保存先への変更は未実装です。

## Chrome と接続するホスト

Chrome 拡張機能はネイティブ メッセージングを使い、端末上のホストを経由して保存データをアプリへ渡します。Windows では、Chrome が参照できるレジストリにホストの manifest の場所を登録する必要があります。[Chrome のネイティブ メッセージング](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging?hl=ja)

### 実行環境とホスト名

所有者は開発と日常利用の両方で主作業ツリーのアプリを直接起動します。MSIX のインストールは導入テストに使います。一般利用者は Microsoft Store から MSIX 版をインストールします。

| 実行環境 | ホスト登録名 | 設定とライブラリ |
| --- | --- | --- |
| 主作業ツリーから直接起動 | `com.dot.host.workspace` | 普段の設定とライブラリを使う |
| 主作業ツリーのコードによる隔離検証 | `com.dot.host.sandbox` | 隔離した設定と検証用ライブラリを使う |
| インストール済み MSIX | `com.dot.host` | MSIX 版の設定と、そこで選んだライブラリを使う |

`workspace` と `sandbox` は、このプロジェクトで定める接尾辞です。`sandbox` は検証用データの隔離を指し、セキュリティ上の隔離を保証する名称ではありません。

Chrome プロファイルの用途とホスト名は独立しています。複数プロファイルで同じ登録を共有でき、日常用・開発用の両プロファイルで普段のライブラリを使う場合は `workspace` へ接続します。別ライブラリで隔離検証する場合は `sandbox` へ接続します。登録名ごとに起動先と設定を分け、ライブラリを振り分けるためだけの独自メッセージを追加しません。

MSIX 版は `workspace` と `sandbox` の登録を上書きせず、主作業ツリー側は MSIX 版の登録を上書きしない構成にします。これらのホスト名への変更は未実装です。`sandbox` 登録を使う隔離検証は一件ずつ実行し、検証コマンドが登録を所有します。セッションを終了してから次の検証を開始します。

### MSIX 版の登録方式

現在は、アプリとホストが `%APPDATA%\dot` を共通の設定領域として使います。MSIX ではファイルやレジストリへの書き込みが仮想化されるため、現在の登録処理をそのまま移すだけでは、パッケージ外で動く Chrome から見えない可能性があります。

ホストの実行コードはパッケージへ同梱します。ホストの manifest は `LocalState\NativeMessaging\com.dot.host.json` に配置する方針です。通常の実パスは `%LOCALAPPDATA%\Packages\<PFN>\LocalState\NativeMessaging\com.dot.host.json` です。実装では Windows の API で `LocalState` の場所を取得し、Chrome 向けのレジストリ登録に manifest の絶対パスを指定します。

`LocalState` は Windows が提供するパッケージ専用の保存領域です。設定をそこへ直接保存すること自体に、仮想化除外は必要ありません。同じパッケージ ID で動くアプリとホストが共有する設定も、この領域を使う方針です。[Windows のアプリデータ](https://learn.microsoft.com/en-us/windows/apps/develop/data/store-and-retrieve-app-data)

この配置は未実装・未検証です。MSIX 化後に、次の項目を実機で確認します。読み取り権限を広げることを前提にせず、通常の権限で Chrome から接続できることを確認します。

- 登録した絶対パスから、パッケージ外の Chrome が manifest を読み取れること。
- 開発用 Chrome からホストを起動し、標準入出力による通信と隔離ライブラリへの保存ができること。
- アプリとホストが同じパッケージ ID と設定保存先を使うこと。
- パッケージ更新後も manifest の参照とホスト接続が機能すること。
- アンインストール時に manifest が削除され、ライブラリは保持されること。Chrome 向けのレジストリ登録が残るかも確認すること。

manifest の保存先と、Chrome 向けのレジストリ登録は別の問題です。MSIX 版は `unvirtualizedResources` を宣言し、Windows 11 の個別除外で `HKEY_CURRENT_USER\Software\Google\Chrome\NativeMessagingHosts\com.dot.host` だけをレジストリ仮想化から除外します。アプリが初回起動時に、このキーの既定値へ manifest の絶対パスを登録し、以後の起動時に登録を検査・修復する構成にします。`workspace` と `sandbox` の登録キーは除外対象に含めません。設定領域全体や HKCU 全体の仮想化は無効にしません。[MSIX flexible virtualization](https://learn.microsoft.com/en-us/windows/msix/desktop/flexible-virtualization)

`unvirtualizedResources` は制限付き機能です。Partner Center の提出時に、Chrome のネイティブ メッセージングに必要な登録を外部プロセスから参照可能にする目的と、除外するキーの範囲を説明して審査を受けます。方式の採用は決定済みですが、Store の承認と実機検証は未完了です。事前照会は、提出前に承認可否を確認したい場合の選択肢です。[制限付き機能の承認手順](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/app-capability-declarations#restricted-capability-approval-process)

仮想化から除外したレジストリ登録は、MSIX のアンインストールでも自動削除されません。manifest はパッケージのデータ領域とともに削除されるため、登録だけが残ることを検証・審査説明の対象に含めます。[レジストリ除外の仕様](https://learn.microsoft.com/en-us/uwp/schemas/appxpackage/uapmanifestschema/element-virtualization-registrywritevirtualization)

### MSIX 版のホスト起動

パッケージ内ホストの起動には App Execution Alias を採用します。ホストの manifest の `path` には、`dot-native-host.exe` という Alias の実際の絶対パスを指定します。Windows が Alias の起動先を管理するため、バージョンを含むパッケージフォルダのパスを manifest に固定しません。コンソールアプリの Alias 起動では、呼び出し元の標準入力・標準出力・標準エラーを継承できます。[Microsoft の Alias 起動](https://learn.microsoft.com/en-us/windows/apps/dev-tools/winapp-cli/guides/dotnet)

同じ `dot.exe` の通常起動からホスト処理へ分岐する案は、2026年10月11日の検証で成立しませんでした。Windows の Electron 通常起動では `process.stdin` が常に EOF になるため、現在のホスト処理が Chrome の入力を受け取れません。この動作は Electron 44.5.1 の公式ソースでも確認しました。[Electron の標準入力処理](https://github.com/electron/electron/blob/v44.5.1/lib/common/init.ts)

対照試験では、同じパッケージ内の Electron を公式の `ELECTRON_RUN_AS_NODE` モードで起動し、既存のホスト処理によるメッセージ往復に成功しました。ただし、試験では親プロセスが環境変数とスクリプトのパスを渡しています。Chrome のホスト manifest だけで、この起動条件を指定できる構成を確認した結果ではありません。[Electron の Node 起動モード](https://www.electronjs.org/docs/latest/api/environment-variables#electron_run_as_node)

App Execution Alias の採用は維持します。通常の標準入出力を扱える専用コンソールの入口から、既存の Electron を Node モードで起動する方式を次の検証候補とします。入口の実装方式は未決定です。ホストは画面を作成せず、接続ごとに独立したプロセスとして動作する構成にします。[Chrome の接続仕様](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging?hl=ja)

最終的な起動経路では、次の項目を確認します。

- Chrome から起動し、標準入出力でメッセージを往復できること。
- ホストがアプリと同じパッケージ ID で動作すること。
- アプリ起動中もホストが独立して動作し、画面を追加しないこと。
- 複数接続でホストを同時に起動できること。
- パッケージ更新後も Alias から接続できること。

### アプリとホストの共有情報

MSIX 版の設定は `LocalState\config.json` を保存元とします。アプリが設定を更新し、ホストはライブラリの保存先など必要な項目を読み取ります。ホスト用に同じ設定を複製しません。設定ファイルの更新はアトミックに行い、ホストが書き込み途中の内容を読まないようにします。

| 情報 | 配置・扱い |
| --- | --- |
| ライブラリの保存先 | `LocalState\config.json`。アプリとホストが共有する |
| テーマ・ウィンドウ位置など | 同じ設定ファイル。ホストは参照しない |
| ホスト manifest | `LocalState\NativeMessaging\com.dot.host.json` |
| 保存済み判定用の索引 | `LocalCache`。ライブラリから再構築できるデータとして扱う |
| メディア・DB・未取込データ・保存処理の復旧記録 | パッケージ外のライブラリ内。アンインストール後も保持する |

アプリの設定、再生成できるデータ、利用者が保持するライブラリを区別します。パッケージ専用のアプリデータはアンインストール時に削除されるため、失ってはいけない利用者のデータを保存しません。[Windows のアプリデータ](https://learn.microsoft.com/en-us/windows/apps/develop/data/store-and-retrieve-app-data)

現在の保存済み判定用の索引は、消失後にホストだけで完全再構築できる構成ではありません。`LocalCache` への移行時には、アプリが閉じていてもライブラリから再構築する処理を実装・検証します。DB への書き込みはアプリが担当し、ホストはライブラリ内の取込キューへ保存します。

## 提出の自動化

GitHub Actions で検証とパッケージ作成を行い、公式 API または公式 CLI でアップロード、審査提出、状態確認を行う構成を予定しています。

| 作業 | Chrome ウェブストア | Microsoft Store |
| --- | --- | --- |
| パッケージ作成・検証 | ZIP を作成・検証 | Windows 上で Forge により MSIX を作成・検証 |
| 認証 | Google の OIDC 連携 | Microsoft Entra の OIDC 連携 |
| アップロード・審査提出・状態確認 | Chrome Web Store API v2 | Microsoft の提出 API／Store Developer CLI |
| 初期登録・掲載内容の確認と編集 | 内蔵ブラウザで開発者ダッシュボードを操作 | 内蔵ブラウザで Partner Center を操作 |

OIDC 連携では、Actions の実行時に短命な認証情報を取得します。dot 用の認証設定と、実際の提出経路での接続確認はこれから行います。[Chrome Web Store API](https://developer.chrome.com/docs/webstore/api/reference/rest)、[Microsoft Store の Actions 連携](https://learn.microsoft.com/en-us/windows/apps/publish/msstore-dev-cli/github-actions)

提出は main を対象とする GitHub Actions の手動実行（`workflow_dispatch`）で行います。所有者がチャットで提出を指示した場合は、対象コミットとバージョンを確認したうえで、エージェントがワークフローを起動できます。所有者が GitHub の実行ボタンを押す必要はありません。通常の main push やタグ作成ではストアへ提出しません。

接続確認と提出を分け、接続確認ではアップロードや提出内容の変更を行いません。掲載内容の編集や下書き保存も、審査提出とは別の操作として扱います。

GitHub Environment は `chrome-web-store` と `microsoft-store` に分け、両方で所有者による承認を必須にします。Environment の設定は未実施です。

## 提出から公開までの設計案

アプリと拡張機能を同じリリースとして検証し、アプリが入手可能になってから拡張機能を公開します。

1. 対象コミット、両方のバージョン、対応する組み合わせを確定する。
2. テストと配備後の実機確認を行い、最新コミットの CI 完了と結果を確認する。
3. ZIP と MSIX を作成・検証する。対象コミット、バージョン、ハッシュを記録し、提出には検証した成果物を使う。
4. 掲載文、画像、権限の理由、データ利用申告、審査員向け手順を確認する。パッケージ更新により申告内容が変わる場合は、提出前に再照合する。
5. 提出の指示に基づき、Microsoft Store へアプリを審査提出する。「Publish now を選ぶまで公開しない」設定を使う。
6. アプリの審査承認後、Environment の承認を経て Microsoft Store で公開する。ダウンロードとインストールができることを確認する。
7. Chrome の審査員にアプリの Store リンクと導入・保存の確認手順を案内し、拡張機能を審査提出する。審査後の公開待ちを指定する。
8. 拡張機能の審査承認後、Environment の承認を経て Chrome ウェブストアで公開する。両ストア版の組み合わせで保存を確認する。
9. 導入手順、配布リンク、変更点を公開する。

初回は上記の順次提出とします。公開準備中のアプリは、Public audience とし、Store 内の検索に表示せず直接リンクから入手できる設定を使います。この設定は非公開配布ではなく、URL を知る人は入手できます。Chrome の審査員が使う Microsoft アカウントを事前登録する必要のある Private audience は使いません。[Store の公開範囲](https://learn.microsoft.com/en-us/windows/apps/publish/publish-your-app/msix/visibility-options)

更新時は、公開済みアプリで候補の拡張機能が動く場合に両ストアの審査を並行できます。新しいアプリが必須の場合は、初回と同じ順序にします。Microsoft Store の公開操作には公式の公開待ちを使います。[Microsoft Store の公開設定](https://learn.microsoft.com/en-us/windows/apps/publish/publish-your-app/msix/manage-submission-options)

Chrome Web Store API v2 では `STAGED_PUBLISH` により審査後の公開待ちを指定できます。審査通過後の公開待ちには最大30日の期限があります。[API の公開方式](https://developer.chrome.com/docs/webstore/api/reference/rest/v2/publishers.items/publish)、[公開待ちの期限](https://developer.chrome.com/docs/webstore/publish)

Actions の提出ジョブの成功は、審査承認や公開完了を意味しません。提出成功、審査承認、公開完了を別々に確認します。提出 API の応答が不明になった場合は、状態確認を先に行い、重複提出を避けます。

Microsoft Store の初回提出と更新提出は分けて設計します。提出ツールが既存の下書きを作り直す場合があるため、掲載内容を保持できる手順を確認します。[MSIX 用 CLI の提出動作](https://learn.microsoft.com/windows/apps/publish/msstore-dev-cli/publish-command)

## 現在の実装と移行の完了条件

現在のアプリは Electron Forge の Squirrel.Windows Maker で `dotSetup.exe`、更新用の `.nupkg`、`RELEASES` を生成します。GitHub Releases の下書きを作成する設定と、GitHub 経由の自動更新処理があります。MSIX Maker の導入、保存先の変更、ストア提出ワークフローはまだ実装していません。

MSIX 化では、パッケージの生成だけでなく、次の動作を確認します。

- クリーンな Windows 環境へのインストール、初回起動、再起動。
- Chrome ウェブストアの拡張機能 ID でのホスト接続と保存。
- パッケージ更新後のホスト接続、設定、既存ライブラリの読み込み。
- アプリと拡張機能の更新に時間差がある場合の互換性、または必要な更新の案内。
- Store によるアプリ更新と、アンインストール後のライブラリ保持。

旧版の設定を初回起動で引き継ぐ処理や、ライブラリ・データベースを自動移行する処理は実装しません。移行のために既存の Squirrel インストーラーへ変更を加えません。所有者の既存ライブラリとデータベースは、アプリの配布処理とは別の移行作業で扱います。その内容と実行時期は別途決めます。

旧 Squirrel の配布物生成と更新処理の撤去は、MSIX 版の動作確認後に行います。主作業ツリーからの直接起動は継続します。移行対象の配布・起動・更新経路に旧方式が残っている間は、移行完了としません。

## 残る確認事項

### 2026年10月11日の検証結果

検証環境は Windows `10.0.26200`、x64 です。Windows `10.0.22000.0` の実機・VMでは検証していません。

最低ビルドの要件調査では、現在選定している Windows 機能と依存ツールに、`10.0.22000.0` より新しいビルドを必要とする根拠は確認されませんでした。レジストリ個別除外の manifest 要件は Build 20348 で、機能説明では Windows 11 からの対応とされています。最低ビルドの候補は `10.0.22000.0` を維持しますが、この環境での動作保証は未確認です。[個別除外の要件](https://learn.microsoft.com/en-us/uwp/schemas/appxpackage/uapmanifestschema/element-virtualization-excludedkey)、[仮想化機能の対応範囲](https://learn.microsoft.com/en-us/windows/msix/desktop/flexible-virtualization)

| x64 の依存ツール検証 | 結果 |
| --- | --- |
| better-sqlite3 13.0.3 | Node 24.16.0 でメモリ DB の作成・INSERT・SELECT 成功 |
| sharp 0.35.5 | Node 24.16.0 でメモリ上の AVIF 生成・metadata 読み取り成功 |
| Meilisearch 1.53.2 | 版表示、隔離 DB での起動、HTTP health の `available` 応答を確認 |
| AVIF 検査器 | libavif 1.4.2・dav1d 1.5.3 の版表示、allocator 検査61件成功 |

これらは依存ツールの個別検証です。製品全体の保存・検索・導入・更新を確認した結果ではありません。

ホスト起動は、専用の開発者登録パッケージ `dot.HostVerification` を使いました。これは MSIX のパッケージ ID と Alias を検証するための展開済みレイアウトであり、Forge で生成した製品 MSIX や Store 配布物の導入試験ではありません。

| ホスト起動の検証 | 結果 |
| --- | --- |
| Alias から Electron 44.5.1 を起動 | 成功。Windows API で検証パッケージの PFN を取得 |
| 通常の Electron 起動で既存ホストの stdin を読む | 失敗。入力は EOF となり、ping 応答なし。直接起動との比較でも同じ結果 |
| Alias 定義の専用引数 | `uap10:Parameters` と `uap11:Parameters` の双方を試したが、この構成では `process.argv` に届かず |
| Alias から Electron の Node モードを起動 | 成功。既存ホストの長さ付き JSON による ping／pong を2プロセスで確認 |
| Node モードのパッケージ ID | 両プロセスで同じ検証パッケージの PFN を取得 |
| 画面・フォーカス | ウィンドウ生成なし。各実行の前後でフォーカスの維持を確認 |
| 検証後の処理 | 専用パッケージを解除し、登録が残っていないことを確認 |

Node モードの成功は、親プロセスが起動条件を渡した対照試験の結果です。Chrome からの接続、製品アプリ起動中の接続、製品 MSIX の更新、`LocalState` の設定共有、アンインストール時の登録処理は未検証です。普段のホスト登録とライブラリは変更していません。
